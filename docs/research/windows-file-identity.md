# Windows file identity: "same folder or inside it?" guard

- **Purpose:** primary-source facts for a fail-closed check "are folder paths A and B the same folder, or is one inside the other?" on Windows, used before a write to a Tekla model folder. A wrong "different" answer is the dangerous direction.
- **Target:** netstandard2.0 library running on .NET Framework 4.8, x64, Windows 10/11, P/Invoke into kernel32.
- **Date accessed:** 2026-11-07
- **Status:** doc-sourced when written. Section "Verified on Windows" (end of file) records what was later run on a real machine; items marked `secondary`/`inferred` elsewhere are NOT from a primary statement.
- **Status tags:** `doc` = Microsoft Learn Win32/.NET page; `spec` = Windows protocol spec (MS-FSCC / MS-FSA / MS-SMB2); `secondary` = Microsoft Learn but indirect, or non-Microsoft; `inferred` = my deduction from cited sources; `not-found`.

## 1. Opening a directory handle for metadata only

- Directories can only be opened with `FILE_FLAG_BACKUP_SEMANTICS` (0x02000000) in `dwFlagsAndAttributes`; "you must set this flag to obtain a handle to a directory". `dwCreationDisposition` must be `OPEN_EXISTING` (3) (CreateFile cannot create directories). · CF (Remarks > Directories; flags table) · `doc`
- `dwDesiredAccess = 0`: "the application can query certain metadata such as file, directory, or device attributes without accessing that file or device, even if GENERIC_READ access would have been denied." · CF · `doc`
- `FILE_READ_ATTRIBUTES` = 0x80 ("the right to read file attributes"). · `en-us/windows/win32/fileio/file-access-rights-constants` · `doc`
- Whether `GetFileInformationByHandleEx(FileIdInfo)` needs `FILE_READ_ATTRIBUTES` on the handle is **not documented** on the Win32 pages. The SMB2 server spec lists the classes that need `FILE_READ_ATTRIBUTES` (FileBasic, FileAll, FilePipe*, FileNetworkOpen, FileAttributeTag) and `FileIdInformation` / `FileInternalInformation` are not in that list. · SMB2 `d64e0451-64a2-425a-848e-52a7dddab7b9` (3.3.5.20.1) · `spec` (server side only; local behaviour `not-found`)
- Share mode: "Access requests to attributes or extended attributes are not affected by this [share mode] flag." `FILE_SHARE_READ`=1, `FILE_SHARE_WRITE`=2, `FILE_SHARE_DELETE`=4 (without it, "no process can open the file or device if it requests delete access"). Using all three (=7) avoids creating a sharing conflict with Tekla or other processes that have the folder open. · CF · `doc` (the choice of 7 is `inferred` from the text)
- Reparse points: without `FILE_FLAG_OPEN_REPARSE_POINT` (0x00200000), "normal reparse point processing" occurs. For symbolic links this is explicit: "If an existing file is opened and it is a symbolic link, the handle returned is a handle to the target." With the flag, "the handle returned is a handle to the symbolic link". · CF "Symbolic Link Behavior"; `en-us/windows/win32/fileio/symbolic-link-effects-on-file-systems-functions` · `doc`
  - Directory junctions and volume mount points are also reparse points; the docs state the general rule (flag = no normal reparse processing) but only spell out the handle-to-target result for symlinks. Junction/mount-point follow-by-default = `inferred` from the general rule. · `en-us/windows/win32/fileio/reparse-points`, `en-us/windows/win32/fileio/naming-a-volume`, `en-us/windows/win32/fileio/mounting-and-dismounting-a-volume` (mounted folders "implemented by using reparse points") · `inferred`
  - **Consequence:** do NOT pass `FILE_FLAG_OPEN_REPARSE_POINT`. With it you get the identity of the link object itself, not the folder it points to, so two aliases would look "different" (dangerous direction).
- `subst` drive: `DefineDosDevice` docs say "MS-DOS device names are stored as junctions in the object namespace" and that the Win32 path conversion uses them to map drive letters. So `S:\x` is rewritten by the object manager to the underlying path before the file system sees it; a handle opened via `S:\x` is a handle to the underlying folder. · `en-us/windows/win32/api/fileapi/nf-fileapi-definedosdevicew` · `doc` (mechanism) / `inferred` (that the resulting FILE_ID equals the one from the real path; confirm with fixture)
- Mapped drive letter to SMB share: a drive-letter mapping is also a DosDevices symbolic link to the redirector path (the cause section of KB 3035277 says drive mappings are "symbolic link objects (DosDevices) that associate the drive letters to the UNC paths"). · `en-us/troubleshoot/windows-client/networking/mapped-drives-not-available-from-elevated-command` · `secondary`
- **Drive-letter mappings are per logon session**, not per machine: "These objects are specific for a logon session and are not shared between logon sessions." With UAC an elevated process and a non-elevated process of the same user are different logon sessions, so `S:` / `Z:` may exist in one and not the other (or point elsewhere). `DefineDosDevice` also creates the device name "in its own Local MS-DOS device namespace" for non-LocalSystem callers. · same KB; `en-us/troubleshoot/windows-server/windows-security/cannot-copy-files-from-mapped-drive-to-local-directory`; DefineDosDevice page · `secondary` / `doc`
  - **Consequence:** resolve and compare in the same process (same token) that will do the write. A drive letter missing in this session makes CreateFile fail → refuse.
- Volume mount point (mounted folder): "users and applications can access the target volume either by using the path to the mounted folder or by using the volume's drive letter"; `C:\MountD\` and `D:\` are two paths to the same volume. `CreateFile` on it follows the reparse point (see junction note above). · `en-us/windows/win32/fileio/volume-mount-points`, `en-us/windows/win32/fileio/naming-a-volume` · `doc`

## 2. `GetFileInformationByHandleEx(FileIdInfo)` and `FILE_ID_INFO`

- Signature: `BOOL GetFileInformationByHandleEx(HANDLE hFile, FILE_INFO_BY_HANDLE_CLASS cls, LPVOID buf, DWORD cb)`; returns 0 on failure, use `GetLastError`. kernel32.dll. · GFIBHE · `doc`
- `FileIdInfo` = **0x12 (18)**, structure `FILE_ID_INFO`. · GFIBHE (table: "FileIdInfo (0x12)") · `doc`
- Layout: `typedef struct _FILE_ID_INFO { ULONGLONG VolumeSerialNumber; FILE_ID_128 FileId; }`; `FILE_ID_128 { BYTE Identifier[16]; }`. Total 8 + 16 = 24 bytes, no padding needed (all natural alignment). · FID; `en-us/windows/win32/api/winnt/ns-winnt-file_id_128` · `doc` (24 bytes = `inferred` arithmetic)
- Minimum OS: FILE_ID_INFO page says client "None supported", server "Windows Server 2012"; the `FILE_INFO_BY_HANDLE_CLASS` page says `FileIdInfo` "is not supported before Windows 8 and Windows Server 2012". Read: Windows 8+/Server 2012+. Windows 10/11 are fine. The two Microsoft pages word it differently (client "None supported") → treat as Windows 8+. · FID; `en-us/windows/win32/api/minwinbase/ne-minwinbase-file_info_by_handle_class` · `doc`
- Supported technologies listed for `GetFileInformationByHandleEx` in Windows 8/Server 2012: SMB 3.0, SMB 3.0 TFO, SMB 3.0 scale-out, CsvFS, ReFS: all "Yes" (NTFS implied). · GFIBHE · `doc`
- Same-file rule (Microsoft): "The file identifier and the volume serial number uniquely identify a file on a single computer. To determine whether two open handles represent the same file, combine the identifier and the volume serial number for each file and compare them." · FID · `doc`
- NTFS `FileId128`: 48-bit MFT index (low 48 bits) + 16-bit sequence number (next 16 bits), high 64 bits always 0. ReFS `FileId128`: low 64 bits = index of the file's parent directory, high 64 bits = index of the file within that directory. · FSA `4e3695bd-7574-4f24-a223-b4679c065b63` (Appendix A, note <48>) · `spec`
- File systems that do not support a 128-bit ID: the call still defines the field: "For file systems that do not support a 128-bit file ID, this field MUST be set to 0, and MUST be ignored." And if a unique ID cannot be established: `0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF`, "and MUST be ignored". So **success with an all-zero or all-0xFF FileId means "no identity"**, not "identity = 0". · FSCC `98860416-1caf-4c80-a9ab-8d61e1ccf5a5` (2.1.10), `e4185a8a-ed8d-4f98-ab55-ca34dc8916e6` (2.4.26); `windows-hardware/drivers/ddi/ntifs/ns-ntifs-file_id_information` · `spec` / `doc`
- Which concrete file systems return a real 128-bit ID: NTFS and ReFS documented (above). FAT/FAT32/exFAT: the Win32 docs only describe the 64-bit index for FAT (below); whether FileIdInfo returns zeros or an error on FAT/exFAT = `not-found`. SMB: see section 3. CsvFS: listed as supported, ID semantics `not-found`.
- Error when the class is unsupported: not documented on the Win32 pages. Spec facts: a server that does not implement SMB 3.x "MUST fail the request with STATUS_NOT_SUPPORTED" for `FileIdInformation`; a too-small buffer gives `STATUS_INFO_LENGTH_MISMATCH` (0xC0000004). The Win32 error these map to (likely `ERROR_NOT_SUPPORTED`/`ERROR_INVALID_PARAMETER`) is `not-found`. · SMB2 `d64e0451-64a2-425a-848e-52a7dddab7b9` (3.3.5.20.1); FSCC `e4185a8a-ed8d-4f98-ab55-ca34dc8916e6` (2.4.26) · `spec`
  - **Consequence:** treat any failure of the call as "cannot prove", never as "different".
- `GetFileInformationByHandle` / `BY_HANDLE_FILE_INFORMATION`: `DWORD dwVolumeSerialNumber` (32-bit) + `nFileIndexHigh/Low` (64-bit index). Microsoft says the index + serial "uniquely identify a file on a single computer. To determine whether two open handles represent the same file, combine the identifier and the volume serial number ... and compare them." GFIBH also says you can compare "to determine if two paths map to the same target; for example, you can compare two file paths and determine if they map to the same directory." · BHFI; GFIBH · `doc`
- But for the 64-bit form: "The ReFS file system ... includes 128-bit file identifiers ... The 64-bit identifier in this structure is not guaranteed to be unique on ReFS." Also: "Depending on the underlying network features of the operating system and the type of server connected to, the GetFileInformationByHandle function may fail, return partial information, or full information for the given file." · BHFI; GFIBH · `doc`
- 64-bit-ID sentinels (same pattern): 0 = not supported; `0xFFFFFFFFFFFFFFFF` = cannot be established. · FSCC `2d3333fe-fc98-4a6f-98a2-4bb805aff407` (2.1.9), `7d796611-2fa5-41ac-8178-b6fea3a017b3` (2.4.27 FileInternalInformation) · `spec`
- Volume serial number caveats: the 32-bit serial in `FILE_FS_VOLUME_INFORMATION` is "an opaque value generated by the file system at format time ... not necessarily related to any hardware serial number ... This value is not required to be unique." The 64-bit `FILE_ID_INFO.VolumeSerialNumber` has the spec text "serial number of the volume"; no uniqueness guarantee beyond the Microsoft "single computer" sentence. A collision between two volumes (cloned disks, same serial) can only make two different folders look "the same" if the file IDs also collide, e.g. both roots (NTFS root has a fixed index) → false "same" = safe direction. · FSCC `bf691378-c34e-4a13-976e-404ea1a87738` (2.5.9) · `spec`; the direction-of-error remark is `inferred`.

## 3. Uniqueness and stability caveats

- **FAT:** the 64-bit file ID is "generated from the first cluster of the containing directory and the byte offset within the directory of the entry for the file"; it "can change over time" (defragmenters; rename to a longer name). `nNumberOfLinks` is always 1 on FAT. So a FAT ID is not a stable identity → a FAT volume can produce "different" for the same folder across time. · BHFI Remarks · `doc`
- **NTFS:** "a file keeps the same file ID until it is deleted"; IDs "are not guaranteed to be unique over time, because file systems are free to reuse them"; "Support for file IDs is file system-specific"; "In some cases, the file ID for a file can change over time." (a deleted-and-recreated folder may reuse an ID: a TOCTOU concern between check and write). · BHFI Remarks · `doc`
- **ReFS:** use the 128-bit ID; the 64-bit one is not unique (above). Spec: ReFS maps only a subset of 128-bit IDs to 64-bit IDs; for values outside the subset the 64-bit ID is `-1`. · FSA `4e3695bd-7574-4f24-a223-b4679c065b63` (Appendix A, note <49>) · `spec`
- 128-bit ID in general: "SHOULD be unique to the volume and stable until the file is deleted" (a SHOULD, not a MUST). MS-FSA: `FileId128` "If available, this value SHOULD be persistent and SHOULD be unique on a given volume." · FSCC 2.1.10; FSA `20ff431e-7c4d-4098-a51c-e6d5614a1c93` · `spec`
- **Network shares (SMB):**
  - Server side: the SMB server answers `FileIdInformation` from its object store: `VolumeSerialNumber = Open.File.Volume.VolumeSerialNumber`, `FileId = Open.File.FileId128`. So an SMB3 server returns its own volume serial and file ID. · FSA `a00d78b9-5a5b-44cc-b389-6c67d53611ee` (2.1.5.12.31) · `spec`
  - SMB < 3.x: server "MUST fail the request with STATUS_NOT_SUPPORTED" for `FileIdInformation`; only `FileInternalInformation` (64-bit) remains. The create context `SMB2_CREATE_QUERY_ON_DISK_ID` gives `DiskFileId` (same as FileInternalInformation) and `VolumeId`, with only a SHOULD for uniqueness. · SMB2 `d64e0451-64a2-425a-848e-52a7dddab7b9`, `9b045a20-e4e7-4747-a504-a72df2f46490` · `spec`
  - SMB1 directory listings: if a remote FS "does not support unique FileId values, then the FileId field MUST be set to zero". · `openspecs/windows_protocols/ms-smb/fbae2fc3-7ff2-4437-b0b0-9536a73bb6ea` · `spec`
  - Whether the Windows **client redirector** forwards the server's values unchanged to `GetFileInformationByHandleEx`, and whether the values are identical via two mapped letters or UNC vs mapped letter to the same share: the spec implies identical (same server object, same Open.File), but no document states it. Non-Windows or non-conforming servers (NAS, Samba) may return zeros, 0xFF.., or unstable values. · `not-found` (client behaviour) · `inferred` (equality)
  - Server-side aliases are invisible to the client: a share's root is the top of what the client can walk. A path `\\srv\models` (share of `D:\data\models`) and `\\srv\data` (share of `D:\data`) have no client-walkable common ancestor; "A inside B" cannot be proven or disproven from the client. · `inferred` (follows from UNC volume = `\\server\share`, see `en-us/dotnet/standard/io/file-path-formats` "device UNCs ... server/share portion forms the volume")
  - Symbolic links stored on a server are evaluated by the client, not the server: the server returns a symbolic-link error response with the target and the client re-issues the open; local-target evaluation "will vary based on client OS". Client policy `fsutil behavior set symlinkevaluation` (L2L, L2R, R2L, R2R) controls which kinds are followed; a disallowed one makes the open fail. · SMB2 `f15ae37d-a787-4bf2-9940-025a8c9c0022`, `a8da655c-8b0b-415a-b726-16dc33fa5827`; `windows-server/administration/windows-commands/fsutil-behavior` · `spec` / `doc`
  - "Windows does not support junctions to directories on remote shares"; junction targets must be local paths. · Sysinternals Junction page `sysinternals/downloads/junction`; also `en-us/windows/win32/fileio/hard-links-and-junctions` (`C:\dir1` -> `Z:\dir2` "aren't permitted") · `doc`
- "File ID may be zero / not unique" summary: zero = unsupported; all-0xFF = cannot establish; 64-bit not unique on ReFS; FAT not stable; volume serial "not required to be unique". All are in the sources above.
- Hard links do not apply to directories. · `en-us/windows/win32/fileio/hard-links-and-junctions` · `doc`

## 4. `GetFinalPathNameByHandleW` (complement, not substitute)

- `DWORD GetFinalPathNameByHandleW(HANDLE, LPWSTR, DWORD cch, DWORD flags)`; Windows Vista+. Returns length without NUL; if buffer too small returns required size including NUL; 0 on error. · GFPN · `doc`
- "A final path is the path that is returned when a path is fully resolved. For example, for a symbolic link named C:\tmp\mydir that points to D:\yourdir, the final path would be D:\yourdir." · GFPN · `doc`
- Flags: `FILE_NAME_NORMALIZED` 0x0 (default; "normalized drive name"), `FILE_NAME_OPENED` 0x8 (opened name, not normalized); volume part: `VOLUME_NAME_DOS` 0x0 (default; drive letter, result uses `\\?\` syntax), `VOLUME_NAME_GUID` 0x1 (`\\?\Volume{GUID}\...`), `VOLUME_NAME_NT` 0x2 (`\Device\HarddiskVolumeN\...`, "can not be used directly by Windows programs"), `VOLUME_NAME_NONE` 0x4 (no drive info). · GFPN · `doc`
- Errors: `ERROR_PATH_NOT_FOUND` when no drive letter exists for the volume (use GUID), and also for `VOLUME_NAME_GUID` on a network share: "Volume GUID paths are not created for network shares." `ERROR_INVALID_PARAMETER` for bad flags; `ERROR_NOT_ENOUGH_MEMORY`. · GFPN · `doc`
- SMB: "does not support queries for normalized paths", so with `FILE_NAME_NORMALIZED` on an SMB handle it queries each path component and "if the user lacks access permission to any one of those components, then the function call fails with ERROR_ACCESS_DENIED". · GFPN Remarks · `doc`
- Third-party drivers that create a drive letter without the Mount Manager: DOS/GUID flags fail, only `VOLUME_NAME_NT` works. · GFPN · `doc`
- Result per alias type:
  - Symlink: resolved to the target (doc example above). · `doc`
  - Junction / mount point: expected to be the target path (same reparse mechanism) · `inferred`
  - `subst` drive: the doc does not say. Expected: underlying path via the object-manager link, since `VOLUME_NAME_DOS` looks up drive letters via the Mount Manager and a `subst` letter is a DosDevices link, not a Mount Manager letter. · `not-found` (primary) / `inferred`; confirm by fixture
  - Mapped drive / UNC to SMB: expected `\\?\UNC\server\share\...` (the `\\?\UNC\` form is documented as the extended UNC syntax in MAXP) · `inferred`
- **Why it matters for "inside" checks (design finding, `inferred`):** walking *text* parents of the typed path only visits ancestors on the typed spelling. If A is `C:\link\sub` and `C:\link` is a junction to `D:\proj\work`, the text parents are `C:\link\sub`, `C:\link`, `C:\` and their IDs are those of `D:\proj\work\sub`, `D:\proj\work`, `C:\`; the ancestor `D:\proj` is never visited, so "A inside D:\proj" is missed. Walk the text parents of **both** the typed path and the final path (from `GetFinalPathNameByHandleW`), and compare every ancestor ID against the other side's ID. Mount-point cases need the typed-path walk too (final path of a mounted volume starts at the mounted volume's root, `C:\Mnt` is not an ancestor in it).

## 5. Long paths on .NET Framework 4.8 with `CreateFileW`

- Win32 default: path limited to `MAX_PATH` (260 incl. NUL). "To extend this limit to 32,767 wide characters, prepend `\\?\`" (use the Unicode `W` API). UNC form: `\\?\UNC\server\share`. · CF; MAXP · `doc`
- Win10 1607+ opt-in without `\\?\` needs BOTH: registry `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled` = 1 (cached per process at first affected call) AND the app manifest `<ws2:longPathAware>true</ws2:longPathAware>`. `CreateFileW` and `GetFinalPathNameByHandleW`, `GetFullPathNameW`, `GetLongPathNameW` are on the opt-in list. · MAXP · `doc`
  - For a netstandard2.0 library hosted by another executable (Tekla plugin or CLI exe) the manifest belongs to the host, which we may not control → do not rely on it. Use `\\?\`. · `inferred`
- `\\?\` "tells the Windows APIs to disable all string parsing and to send the string that follows it straight to the file system": no forward slashes, no `.` or `..`, no relative paths (relative paths stay limited to MAX_PATH). Also skips normalization and trailing dot/space trimming. · MAXP; NAMING; `en-us/dotnet/standard/io/file-path-formats` ("Skip normalization") · `doc`
- So: normalize first, then prefix. `GetFullPathNameW` (or `Path.GetFullPath`) does the normalization and "supports arbitrary length paths ... without `\\?\`". Paths already starting with `\\?\` are still normalized if passed to GetFullPathName. · `file-path-formats` · `doc`
- .NET Framework managed layer: from apps that **target 4.6.2** (or that opt in via AppContext switch `Switch.System.IO.UseLegacyPathHandling=false` and `Switch.System.IO.BlockLongPaths=false`) long paths (up to 32K) and `\\?\` are supported by `System.IO`, and `Path.GetFullPath` defers to OS `GetFullPathName`. Apps targeting < 4.6.2 get the legacy 260 check even on a 4.6.2+ runtime. Our direct P/Invoke is not subject to the managed MAX_PATH check, but `Path.GetFullPath` called from the library is, so the host's target framework matters. · `en-us/dotnet/framework/migration-guide/retargeting/4.6.x`; `en-us/dotnet/framework/migration-guide/mitigation-path-normalization`; `file-path-formats` ("On .NET Framework only, to skip the MAX_PATH check ...") · `doc`
  - To remove host dependence, P/Invoke `GetFullPathNameW` directly. · `inferred`
- Prefix conversion: `C:\a\b` → `\\?\C:\a\b`; `\\server\share\a` → `\\?\UNC\server\share\a`; a path already starting `\\?\` is left as is. `\\.\` is the device namespace; do not use for files. · MAXP; NAMING · `doc`
- Drive letter forms like `S:` (subst) and `Z:` (mapped) work after the `\\?\` prefix (`\\?\S:\...`) because the prefix goes to the same DosDevices namespace (`\\?\` and `\\.\` "identify a drive by its drive letter"). · `file-path-formats` (DOS device paths) · `doc` (support of the letter) / `inferred` (for subst/mapped)
- Drive-relative (`C:foo`) and current-directory-relative paths are process-state dependent; reject non-fully-qualified input rather than normalizing silently (`Path.IsPathFullyQualified` is not in net48; check manually). · `file-path-formats` · `doc` (hazard) / `inferred` (rule)

## 6. Permissions and errors

- Directory ACLs: access is checked on the object being opened; "the security descriptor of a parent directory is not used to control access to any child". Traversal: `FILE_TRAVERSE` on ancestors is only enforced if `BYPASS_TRAVERSE_CHECKING` (SeChangeNotifyPrivilege) is removed; by default, "users are assigned" it and it "ignores the FILE_TRAVERSE access right". Default holders include Users, Everyone, Administrators, Backup Operators, Local/Network Service. · `en-us/windows/win32/fileio/file-security-and-access-rights`; `en-us/windows/win32/fileio/file-access-rights-constants`; `en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/security-policy-settings/bypass-traverse-checking` · `doc`
- Opening a directory handle with access 0 or `FILE_READ_ATTRIBUTES` therefore needs, by default, only that right on the folder's own ACL (access 0 "even if GENERIC_READ would have been denied" per CF). Hardened systems that removed Bypass traverse checking need traverse on every ancestor. · CF; above · `doc` / `inferred`
- `FILE_FLAG_BACKUP_SEMANTICS` does not itself bypass ACLs: "Appropriate security checks still apply when this flag is used without SE_BACKUP_NAME and SE_RESTORE_NAME privileges". A process with those privileges enabled overrides file security checks. · CF; File security page · `doc`
- Errors from CreateFile: `INVALID_HANDLE_VALUE`; `ERROR_FILE_NOT_FOUND` (2) for a missing target with OPEN_EXISTING; `ERROR_ACCESS_DENIED`; `ERROR_SHARING_VIOLATION`. Generic list in `en-us/windows/win32/fileio/creating-and-opening-files` (ERROR_FILE_NOT_FOUND, ERROR_ACCESS_DENIED, ERROR_SHARING_VIOLATION). Network-specific codes, `ERROR_PATH_NOT_FOUND` (3) vs `ERROR_BAD_NETPATH` etc., and symlink-evaluation-disabled error: `not-found`. · `doc`
- Reparse limits: max 63 reparse points on a path (31 if the target is a fully-qualified path); a symlink to a missing target gives `ERROR_FILE_NOT_FOUND`. · `en-us/windows/win32/fileio/reparse-points`; `en-us/windows/win32/fileio/symbolic-link-programming-considerations` · `doc`
- Open failure on any ancestor means that ancestor's identity is unknown, so containment cannot be excluded → refuse (policy, `inferred`).

## 7. P/Invoke details for net48 / netstandard2.0

- `DllImport("kernel32.dll", SetLastError = true, CharSet = CharSet.Unicode)`; `CreateFile` can return `SafeFileHandle` directly; check `IsInvalid`; get the error with `Marshal.GetLastWin32Error()` right after the failing call. Microsoft's own example is this pattern. `SafeFileHandle` is in `netstandard.dll`. · `en-us/dotnet/api/microsoft.win32.safehandles.safefilehandle` · `doc`
- `ExactSpelling = true` with explicit `...W` names is the recommended setting; `CharSet.Unicode` should be explicit when strings are present. · `en-us/dotnet/standard/native-interop/best-practices` · `doc`
- .NET Framework quirk: "On .NET Framework, GetLastWin32Error can retain error information from one P/Invoke call to the next" (on .NET Core it is cleared before each call). So read it only on a failure return. · `en-us/dotnet/api/system.runtime.interopservices.marshal.getlastwin32error` · `doc`
- `SafeFileHandle` as an `[In]` argument to `GetFileInformationByHandleEx` / `GetFinalPathNameByHandleW` is fine (marshals as the handle). · `inferred` (standard marshalling; `doc` example only for CreateFile return)
- `FILE_ID_INFO` struct in C#: `[StructLayout(LayoutKind.Sequential)] struct FILE_ID_INFO { public ulong VolumeSerialNumber; public ulong FileIdLow; public ulong FileIdHigh; }` (24 bytes, matches `ULONGLONG + BYTE[16]`; avoids array marshalling; order of bytes within the two ulongs does not matter for equality as long as both sides use the same struct). ## Recommended implementation

Per path P (A = open model folder, B = working copy, C = original; compare all pairs):

1. **Require fully qualified, normalized input.** Reject relative and drive-relative paths. Normalize with `GetFullPathNameW` (P/Invoke), then add `\\?\` (`\\?\UNC\...` for UNC). Do not hand-edit after the prefix is added.
2. **Open:** `CreateFileW(path, FILE_READ_ATTRIBUTES (0x80), FILE_SHARE_READ|FILE_SHARE_WRITE|FILE_SHARE_DELETE (7), NULL, OPEN_EXISTING (3), FILE_FLAG_BACKUP_SEMANTICS (0x02000000), NULL)`. **Never** `FILE_FLAG_OPEN_REPARSE_POINT`. `SetLastError=true`, returns `SafeFileHandle`; `using` / dispose. Failure of any open → **cannot prove → refuse**.
3. **Identity:** `GetFileInformationByHandleEx(h, 18 /*FileIdInfo*/, &FILE_ID_INFO, 24)`. Identity is valid only if the call succeeded AND `FileId` is not all-zero AND not all-0xFF. Then key = `(VolumeSerialNumber, FileId[16])`.
   - If FileIdInfo fails or yields no ID: fall back to `GetFileInformationByHandle` key = `(dwVolumeSerialNumber, FileIndexHigh:Low)`, valid only if index is not 0 and not `0xFFFFFFFFFFFFFFFF`. The 64-bit ID is not unique on ReFS (BHFI), and detecting ReFS needs `GetVolumeInformationByHandleW` (a Gap); ReFS sets the 64-bit ID to -1 when the 128-bit ID cannot be mapped (FSA `4e3695bd-7574-4f24-a223-b4679c065b63`, note <49>), which the sentinel check rejects, but a mapped ReFS 64-bit value is not proven unique. So treat a 64-bit-only key as weaker: it may prove "same" but never "different" on its own (see step 6). A 64-bit key may be compared only with another 64-bit key (never mix with a 128-bit key). If neither works → cannot prove → refuse.
4. **Same-folder test:** keys equal ⇒ same folder ⇒ refuse (equal is always safe to trust: a false "same" only blocks).
5. **Containment test (A inside B, B inside A):** build the ancestor set of each side from (a) the text parents of the normalized typed path up to the drive/share root and (b) the text parents of the final path from `GetFinalPathNameByHandleW(h, ..., FILE_NAME_NORMALIZED | VOLUME_NAME_DOS)`; if that fails, retry with `VOLUME_NAME_GUID` (`\\?\Volume{GUID}\...`, openable, local volumes only; not created for network shares per GFPN); `VOLUME_NAME_NT` results (`\Device\...`) can be opened only with the `\\?\GLOBALROOT` prefix (NAMING, "NT Namespaces"; `doc`, untested) and `FILE_NAME_OPENED` is not a resolved path, so do not use either as a substitute. If all fail, cannot prove, refuse. Open each ancestor as in step 2 and take its key. If any ancestor key of X equals the key of Y (and the reverse), refuse.
   - Any ancestor that cannot be opened or has no valid identity → cannot prove → refuse. Do not skip it.
   - Hold the handles open until the decision is made and re-check immediately before the write; IDs can be reused after deletion and NTFS folders can be replaced (TOCTOU is not removable by this check).
6. **"Different" is allowed only when ALL hold:** every key for both sides is a valid 128-bit key (a 64-bit-only key never supports "different", because it is not unique on ReFS and is unstable on FAT); no key matched; and the ancestor walks were complete. Anything else → "cannot prove" → refuse.
7. **Remote paths (UNC, mapped to SMB, or `DRIVE_REMOTE`):** treat "different" as unprovable unless the policy explicitly accepts the risk. Reasons: client cannot walk above the share root; server-side junctions/aliases are invisible; redirector ID behaviour is undocumented; non-Windows servers may return zero/unstable IDs. (Design recommendation, `inferred`.)
8. **Process context:** resolve and compare in the same process/token that performs the write (per-logon-session drive mappings).
9. **Failure to detect FAT/exFAT stability:** if the volume file system is FAT/FAT32/exFAT (via `GetVolumeInformationByHandleW`, not researched here) refuse "different" (FAT IDs unstable; FileIdInfo behaviour unknown).
10. **Limit of the "different" verdict (dangerous direction).** The ancestor walk only proves containment in the resolved tree. It cannot see A being reachable through a junction, symlink or mount point *inside* B's subtree (e.g. `B\j` pointing to A or to an ancestor of A): the check says "different" but a writer that follows links into B writes into A. Either the writer must not follow reparse points (open with `FILE_FLAG_OPEN_REPARSE_POINT` and reject `FILE_ATTRIBUTE_REPARSE_POINT` entries) or B's subtree must be scanned for reparse points before the write. Callers must treat "different" as "no alias found in the resolved ancestor chains", not as proof of disjointness. (`inferred`)

## Gaps

- **Containment through links inside the other tree** (e.g. `B\j` -> A): not detectable by an ancestor walk; needs a non-following writer or a reparse-point scan of B's subtree (see Recommended step 10). Not researched further.
- Win32 error code returned by `GetFileInformationByHandleEx(FileIdInfo)` when the file system/driver does not support it (and whether FAT/FAT32/exFAT return an error or a zero `FileId`). Only NT status codes from the specs found.
- Whether `FileIdInfo` requires `FILE_READ_ATTRIBUTES` on the local handle (only the SMB-server rule is specified; local behaviour undocumented).
- Windows SMB **client** behaviour: whether VolumeSerialNumber/FileId are passed through unchanged and equal across two drive letters and UNC to the same share; behaviour against non-Windows servers; which Win32 errors appear for disabled symlink evaluation or unreachable server.
- Documentation that `CreateFile` follows directory junctions and mount points by default (docs spell this out for symlinks; junction/mount point is the general reparse rule only).
- What `GetFinalPathNameByHandleW` returns for `subst` drives and for mapped drives (not documented; expected underlying path / `\\?\UNC\...`); how FileId of a `subst` root compares with the FileId from the real path (expected equal).
- Privilege needed to create junctions (inferred none from MS-FSA) and volume mount points (`SetVolumeMountPoint`); admin requirement for creating SMB shares and attaching VHDs for fixtures.
- FILE_ID_INFO minimum-client wording conflict ("None supported" vs "Windows 8").
- Primary statement that .NET Framework 4.8 has no managed file-ID API (absence claim only).
- Behaviour of the .NET Framework path code for a netstandard2.0 library depends on the host executable's target framework / quirk switches; not verified for the actual Tekla host.
- CsvFS FileId semantics; ReFS-on-SMB behaviour; whether `FILE_NAME_NORMALIZED` vs `FILE_NAME_OPENED` differ for junction/mount-point handles.
- GetVolumeInformationByHandleW (file system name) use and FAT detection were not researched.

## Verified on Windows (2026-11-07)

Windows build 26200, NTFS `C:`, not elevated, `TeklaCore.dll` loaded in PowerShell 5.1
(.NET Framework 4.8). Probes by the S1a author and by two independent reviewers. The CI job
`dotnet` is set up to repeat the fixture cases on windows-latest (`Win32FolderResolverTests`);
its first run is still pending.

- OneDrive Files-On-Demand entries carry the reparse attribute (161 of 173 on the probe
  machine), so the link scan refuses models inside synced folders.

- Directory junctions are followed by default (no `FILE_FLAG_OPEN_REPARSE_POINT`): a junction
  gives the target's file ID and final path. Answers the junction gap above.
- A `subst` letter gives the target's file ID, and `GetFinalPathNameByHandleW(VOLUME_NAME_DOS)`
  returns the real `\\?\C:\...` path, also for the subst root.
- A mapped letter or subst onto `\\localhost\C$` gives a `\\?\UNC\...` final path; loopback SMB
  returned the same file ID as the local path.
- A handle opened with `FILE_READ_ATTRIBUTES` is enough for `FileIdInfo` and
  `GetVolumeInformationByHandleW`.
- NTFS file IDs: high 64 bits 0, low 64 bits = sequence + index, so `FILE_ID_128` maps to
  (low = bytes 0–7, high = bytes 8–15) as implemented.
- Final paths of 370–393 characters are read in full (buffer regrow path).
- A normal user can create junctions (`mklink /J`), hard links (`mklink /H`) and subst drives;
  `mklink /D` (directory symlink) was denied without the privilege.
- `robocopy /E /SJ` copies a junction as a junction that still points at its old target.

Still unverified: directory symlinks and mount points (need privilege), ReFS, FAT/exFAT, DFS,
shadow copies.
