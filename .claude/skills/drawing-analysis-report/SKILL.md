# Drawing analysis report

Owner: `doc-reader`, in a fresh dispatch after the reading, so the report is built from the
artefacts rather than from memory of the reading. The engineer must be able to audit every
figure in minutes. You write; you do not re-read the drawings and you raise no questions. Every
number and claim you print names the artefact it comes from. A figure the skill asks for that no
artefact holds is printed as `không có trong artefact`; a gap you notice (a `low` value nobody
asked about, a missing count) goes in §9 under **Chưa hỏi** and in your final message to the
orchestrator, who sends it back to the reader.

## Inputs

Run every `harness` command through the one invocation the dispatch names (`uv run --project <checkout> harness …` with absolute
paths: structural-drawing-reader tools.md, first paragraph). A harness whose `--help` lacks `part` or `takeoff` is the wrong one: stop
and name the command you ran.

In `projects/<id>/work/` (`W`): `inventory.json`, `read-log.json`, `structure-summary.json`,
`structure/<file>.{sheets,grids,levels}.json`, `grid-systems.json` (+ SVGs), `callouts.json`,
`marks.json`, `reader-findings.json`, `answers.json`; `uv run harness status projects/<id>/work`,
whose `parts[]` give each part's `status`, `blocking_open_ids` and `ready`; `W/parts/<part>/notes.md`
for every part (scope, `unread` and `absent` lines with question ids, tool gaps, `needs:` lines);
`projects/<id>/questions.md` (render it first with `uv run harness questions-md
projects/<id>/work`); `W/reading-record.md` and each part's latest `W/parts/<part>/review/round-<n>/review.md`
when present: §2 takes the ranked problems and §5 the K1–K14 lines of `W/parts/all-assembly/notes.md` and the review verdicts;
§9 lists every `unread` and `absent` line of the notes with its question id. Missing
`grid-systems.json`, `structure-summary.json` or `reader-findings.json`, or no `parts[]` in `status`
→ stop: the reading is not done.

## Part A — `projects/<id>/01-analysis.md`

Vietnamese, these sections in order:

1. **Kết luận** — 3–5 lines: can modelling be planned, and what blocks it: the `gate1.reasons`
   count, then separately the open blocking questions that block lot specs (callouts, marks).
2. **Vấn đề** — Critical / Major / Minor: reason, where, question id. The ranked problems of
   `all-assembly/notes.md` and every defect Part C hands back (see its step 6) go here.
3. **Hồ sơ đã nhận** — per file: format, converter, outcome, confidence cap, unit and whether
   it is confirmed, sheet count, changes since last intake.
4. **Bộ bản vẽ** — per file, sheets by class from the `sheet_class` findings (finding id,
   title entry id); sheets without a class with their question id; drawing list status.
5. **Cách đã đọc** — the commands run, the converter (version if the read log has it, else
   `không ghi nhận`), fallbacks, how confidence was capped, the method of each value class
   (`dxf_entity`, `derived`, `engineer_answer`, `vision`, `measured from linework`), and how much text the font gate
   blocked per file (`list-sheets` `blocked_text_count`) with its font question ids; the parts
   read (`parts[]`: id, status), and each part with a `status` other than `locked`, marked `chưa khóa`.
6. **Thông tin chung** — `note_item` and `structural_system` findings: value verbatim, sheet,
   finding id, entry ids, confidence. A `measured` finding, or a `cross_check` with evidence,
   prints `evidence.source` (`geometry/<name>.json`) and `evidence.items` (the `G-` ids, or
   their count with the first and last) instead of entry ids; the same wherever a finding is
   cited. A measured finding that `finding list` shows with `stale_reasons` is not printed as a
   figure: say it is stale.
7. **Lưới trục và cao độ** — per grid system: labels, spacings, coordinate string (drawing
   units, and mm only where the system has it), evidence counts, flags, SVG link, selection
   and X/Y status; levels: storey levels confirmed or not. Everything unanswered is marked
   `chờ xác nhận`.
8. **Cấu kiện và ký hiệu** — from `marks.json`: mark counts per sheet, tables (blocked headers
   named), matched / schedule-only / plan-only counts, notation variants and size conflicts
   with question ids; from `callouts.json`: parsed vs unparsed counts per reason; the `measured` findings per member
   family: value, sheet, finding id, source, items (count, first, last), confidence, render
   check. Quantities only where a measured finding backs them; a total is a hand sum of those
   findings, labelled so.
9. **Những gì có thể sai** — heuristics relied on, unverified conventions, low-confidence groups
   with counts, single-source grid systems, files read only partially, blocked text.
10. **Câu hỏi mở** — blocking open first, ids as in `questions.md`. A listed value read from linework alone has a
    blocking family question (`reader_family_linework`): list it here like any blocking question.

*Done when* every number in the report appears in a named artefact, and every `low` or
unconfirmed value carries a question id or is listed under **Chưa hỏi** in §9.

## Part C — `projects/<id>/takeoff/` (take-off plan, same dispatch, after Part A)

Required to close step 2. `harness takeoff` writes every heading, table, source, confidence,
status and lot line from the part artefacts, so none of it is typed. You write two short prose
slots per part file. Vietnamese prose. The engineer's page and any 3D draft are generated from
these files. The commands printed inside the take-off files name the work folder relative to the take-off folder (for example
`../work`): the engineer runs them from that folder. Run, with `W` = `projects/<id>/work` (each `takeoff` command takes `[--out DIR]`):

1. **Check the locks.** `uv run harness part check W --part <id>` for every `locked` part of
   `status` `parts[]`, then `uv run harness status W`: a changed input moves a part's hash and
   it reads `reopened` or `stale_input`. Name each such part in your final message; the
   orchestrator records `reopened`, then `checked`, `reviewed` and `locked` again.
   *Done when* every part is `locked`, or named.
2. **Render.** `uv run harness takeoff render W --all` writes `<nn>-<part>.md` for every part
   `checked`, `reviewed` or `locked` (an unlocked one reads `chưa khóa (…)`); the stdout
   `skipped` lists the parts not yet eligible: print them in Part A §9. Rerunning keeps the slots.
3. **Plan.** `uv run harness takeoff plan W` writes `00-plan.md`: conclusion, parts in order,
   lots, open questions. It has one lot row (lot `—`) per bookkeeping part that holds open blocking questions, and the `chặn mọi lô`
   row is `project_blocking_ids` of `harness status`. Run it before `check`, which reports a missing plan.
4. **Fill the slots.** In each part file replace `_(chưa viết)_` in `<!-- ai:method -->` (§ 1:
   two to four sentences on how the values were obtained: printed text, schedule row, measured
   from linework) and in `<!-- ai:reason -->` (§ 4: one sentence on why the confidence level
   printed above it is that level). Read both from the file's own generated lines. Write in the
   engineer's words (Style) with no id, no backtick, no number the file's generated lines do not
   hold; `check` names the barred jargon words. Edit nothing else: the next render overwrites it.
5. **Check.** `uv run harness takeoff check W` until exit 0. `generated_differs`: rerun
   `render --all`, then `plan`. Any `ai_*` problem: rewrite that slot. `file_unexpected`: name the
   file in your final message. A value, cell, status or lot you think wrong is never typed over.
6. **Hand defects back.** A value that looks wrong, a known defect of a part's latest
   `review.md` or in a defect list the orchestrator gives you: list it in Part A §2 with its
   source, and in your final message for the reader to fix as a row or a question; then rerun
   steps 2 to 5.

*Done when* `takeoff check` exits 0, every part of Part A §5 but `scout` and `all-assembly` has a file linked in `00-plan.md`,
and every `skipped` or unlocked part is named.

## Part B — `projects/<id>/04-info-matrix.csv` (gate 3, workflow step 7)

One row per member **instance** and field:
`file, sheet, mark, instance_ref, field, value, unit, source_entry, method, confidence, status, question_id`.
`instance_ref` locates the instance (grid ref + level when known, else the text entry id).
Fields: every field `schemas/spec.schema.json` needs for its member type (profile, material,
start, end, rotation…). `status`: `ok` only when confidence ≥ medium and no open question
touches it; `provisional` when low or asked; `missing` when no artefact gives it; `conflict`
when two sources disagree. A measured value: `method` = `measured`, `source_entry` =
`geometry/<name>.json#<G-id>`. *Done when* every member instance listed in Part A §8 has a row for
every spec field.

## Style

Conclusion first, short sentences, units always printed. A word found only in font-blocked text
appears nowhere in the report, not even as a topic name; blocked items are cited by entry id and
font question. The engineer's words: bản vẽ, tờ,
lưới trục, cao độ, ký hiệu, bảng thống kê, câu hỏi chặn. Tool names appear only as the command
the engineer would run. Print a script's numbers as given; a total is either a script's or a hand sum of cited findings
labelled `cộng tay`.
